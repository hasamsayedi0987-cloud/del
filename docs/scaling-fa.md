# معماری مقیاس‌پذیری دل — مسیر رسیدن به یک میلیون تماس هم‌زمان

> تاریخ: ۱۴ آبان ۱۴۰۵ · نسخهٔ API: 1.5 · این سند پاسخ فنی به نیاز «۱٬۰۰۰٬۰۰۰ تماس هم‌زمان بدون مشکل» است.
> چیزی که امروز در کد هست و چیزی که برای هر پلهٔ مقیاس باید اضافه شود، هر دو اینجا شفاف نوشته شده است.

## ۱) نکتهٔ بنیادی: بایت‌های صدا/تصویر از API عبور نمی‌کنند

کل مدیای تماس (صوت و تصویر) مستقیماً بین کلاینت‌ها و سرور **LiveKit (SFU)** جریان دارد؛
API نست‌جی‌اس فقط «signaling» است: صدور توکن (`calls.service.ts`)، زنگ (`call.incoming`)،
پاسخ/پیوستن/ترک (`call.accepted` / `call.ended`). یعنی ظرفیت تماس‌ها تقریباً مستقل از ظرفیت API است و
با **خوشهٔ SFU** رشد می‌کند، نه با سرورهای NestJS.

- هر تماس = یک اتاق LiveKit به نام `call:{callId}`.
- هر عضو توکن JWT اختصاصی با grantهای `video.roomJoin` می‌گیرد.
- تماس گروهی ۱۰ نفره = هر عضو ۱ آپلود (صوت ~۲۴kbps + تصویر ~۱Mbps) و ۹ دانلود ≈ **۹٫۳Mbps مصرف دانلودِ هر عضو**.

## ۲) چه چیزهایی همین حالا در کد آمادهٔ مقیاس است

| قابلیت | کجا | توضیح |
| --- | --- | --- |
| اداپتر Redis برای Socket.IO | `messages.gateway.ts → afterInit` | با `REDIS_URL` رویدادها/اتاق‌ها بین همهٔ نمونه‌های API منتشر می‌شود — precondition خوشه‌شدن |
| وضعیت اعضای تماس گروهی مشترک | `calls.service.ts → membersAdd/Remove` | با `REDIS_URL` روی Redis ذخیره می‌شود (کلید `del:call:members:{callId}`، TTL ۶ ساعت)؛ بدون Redis هم روی حافظهٔ همان نمونه کار می‌کند |
| اتاق‌بندی رویدادها | `conv:{id}` / `user:{id}` | زنگ گروهی به اتاق شخصی هر عضو می‌رود؛ O(اعضا) نه O(بوت‌استرپ) |
| signaling بدون حالت (stateless) | کل `calls.service` | فقط وابسته به Postgres/Redis — نمونهٔ API را می‌شود افقی بالا برد |
| SFU خارج‌شده از API | LiveKit | افزایش ظرفیت مدیا با افزودن نود SFU، بدون تغییر کد |
| تایمر زنگ + sweep یتیم‌ها | `armRingTimer` / `sweepStaleRinging` | تماس‌های رهاشده منابع نمونه را نمی‌گیرند |

## ۳) پله‌های مقیاس و الزامات هر پله

### پلهٔ ۰ — امروز (Render Free)
- یک نمونهٔ API + Postgres ابری + LiveKit ابری (LiveKit Cloud رایگان شروع می‌شود).
- ظرفیت واقعی: **~۵۰۰–۱٬۵۰۰ اتصال WS هم‌زمان و ~۱۰۰–۳۰۰ تماس هم‌زمان** (محدودیت RAM ۵۱۲MB و CPU اشتراکی).
- برای محیط تولید کوچک کافی است؛ برای «میلیون» خیر — و ادعای غیر از این نادرست است.

### پلهٔ ۱ — تا ~۱۰٬۰۰۰ تماس هم‌زمان (~۱۰۰ هزار کاربر فعال روزانه)
- **API**: ۲–۴ نمونه پشت Load Balancer با **sticky session** (الزامی برای socket.io با polling؛ با `transports:['websocket']` هم کافی است cookie بماند).
- **Redis**: یک نمونهٔ مدیریت‌شده (Upstash/Redis Cloud) — اداپتر socket.io + وضعیت تماس گروهی + presence.
- **SFU**: ۱–۲ نود LiveKit اختصاصی (هر نود با ۸vCPU/16GB حدود ۲–۵ هزار مسیر صوتی/تصویری فعال بسته به رزولوشن) یا LiveKit Cloud.
- **Postgres**: PgBouncer + ایندکس‌های `call(status, startedAt)` و `participant(userId)`.
- پیکربندی فقط با env: `REDIS_URL` + چند نمونهٔ API — بدون تغییر کد.

### پلهٔ ۲ — تا ~۱۰۰٬۰۰۰ تماس هم‌زمان
- **SFU خوشه‌ای**: LiveKit با etcd/redis backend، چند نود در ۲–۳ ریجن؛ توزیع اتاق‌ها خودکار است.
- **API**: ۱۰+ نمونه، autoscale روی CPU و تعداد اتصال WS.
- **Redis**: Redis Cluster (شاردینگ کانال‌های pub/sub).
- **Postgres**: read replica برای `history()` و لیست‌ها؛ فقط نوشتن روی primary.
- **مدیا**: انتخاب SFU نزدیک به کاربر (ریجن‌محور) — کلید `LIVEKIT_URL` را می‌شود در `auth.me` بر اساس ریجن برگرداند.

### پلهٔ ۳ — ۱٬۰۰۰٬۰۰۰ تماس هم‌زمان
عدد واقعی: یک میلیون تماس ۱۰ نفره = ۱۰ میلیون شرکت‌کنندهٔ مدیایی؛
با فرض صوت (۲۴kbps) + تصویر ۳۶۰p (~۵۰۰kbps آپلود هر ناشر):
- ظرفیت آپلود تجمعی ≈ ۱۰M × ۵۲۵kbps ≈ **۵٫۲Tbps**؛ دانلود SFU چند برابر.
- یعنی به ترتیبِ بزرگ‌نمایی **~۱٬۵۰۰ نود SFU با کارت شبکهٔ ۱۰Gbps** در ده‌ها ریجن لازم است (یا معادل LiveKit Cloud Enterprise).
- **signaling**: ۵۰–۱۰۰ نمونهٔ API (هر نمونه ~۵۰–۱۰۰ هزار WS) با Redis Cluster؛ sticky session در LB (nginx `ip_hash` یا AWS ALB sticky).
- **دیتابیس**: نوشتن تماس فقط insert + دو update (بدون چت در همان جدول) — با پارتیشن‌بندی ماهانهٔ `Call` و نگهداری آبسترهٔ آمار.
- **اهرم‌های مهم در همین طراحی**: اتاق `user:{id}` به‌جای broadcast، زنگ فقط به اعضا، توکن کوتاه‌عمر، و این که مدیا هرگز از API نمی‌گذرد — همین چهار تصمیم است که «میلیون» را ممکن می‌کند.

## ۴) سرعت برقراری (صحت‌سنجی مسیر فعلی)

مسیر یک تماس: REST `POST /calls` → insert + emit → WS زنگ → `POST /calls/:id/accept` → sign JWT + emit → کلاینت `room.connect`.
- هیت سرد Postgres روی Render Free بزرگ‌ترین تأخیر است (همین که keepalive workflow هر ۱۰ دقیقه پینگ می‌دهد، مشکل خواب سرور را حل می‌کند).
- مابقی مسیر فقط ۲ کوئری + ۱ امضای JWT است؛ در پلهٔ ۱ به‌جای Postgres، «مشغولی» را می‌توان با Redis key انجام داد (نیاز آینده؛ الان با count ایندکس‌شده هم <۱۰ms است).

## ۵) چک‌لیست عملی برای رسیدن به پلهٔ ۱ همین هفته

1. `REDIS_URL` روی Render ست شود (Upstash رایگان شروع می‌شود) → اداپتر socket.io خودکار روشن می‌شود.
2. دو نمونهٔ API (Render paid) پشت LB با sticky session.
3. LiveKit Cloud به‌جای LiveKit تک‌نودی؛ `LIVEKIT_URL/API_KEY/SECRET` فقط env می‌ماند.
4. `keepalive.yml` بماند؛ مانیتورینگ: `/api/v1/health` + متریک اتصال WS در لاگ Render.

## ۶) مرزهای صادقانهٔ نسخهٔ ۱٫۵

- تماس گروهی تا سقف اعضای گروه کار می‌کند (پیشنهادی ≤ ۱۲ نفر با تصویر؛ با صوت بیشتر) — LiveKit خودش SFU می‌کند و سقف نرم‌افزاری جداگذاری نشده تا با ظرفیت SFU هم‌راستا باشد.
- شمارش اعضای تماس گروهی با REDIS_URL بین نمونه‌ها دقیق است؛ بدون Redis فقط روی تک‌نمونه درست است.
- «end برای همه» در گروه فقط با تماس‌گیرنده است؛ اعضای دیگر با «ترک تماس» بیرون می‌آیند.
