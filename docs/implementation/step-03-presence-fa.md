# گام ۳ — حضور، تایپینگ، رسید خواندن و همگام‌سازی آفلاین

> وضعیت: اجرا و تست دود شده — **۱۷/۱۷ سبز** (`scripts/smoke-step3.js`) + رگرسیون گام ۱ (۸/۸) و گام ۲ (۲۱/۲۱)

## ۱. هدف

چهار قابلیت زنده‌سازی چت که در معیار پذیرش گام ۲ تعریف شده بود:

1. **حضور (presence):** آنلاین / آخرین بازدید — بلادرنگ برای هم‌مکالمه‌ها
2. **تایپینگ:** «در حال نوشتن…» بدون ارسال درخواست اضافی
3. **رسید خواندن:** ✓ (ارسال شد) → ✓✓ (خوانده شد) بلادرنگ
4. **همگام‌سازی آفلاین:** پیام‌های دوره قطع، بدون گپ

## ۲. حضور (presence)

### مدل داده

کلید Redis: `del:presence:{userId}` = JSON `{online, lastSeen}`

- وضعیت `online` با **TTL ۷۵ ثانیه** ذخیره می‌شود؛ کلاینت هر **۲۵ ثانیه** رویداد `presence.heartbeat` می‌فرستد و سرور TTL را تمدید می‌کند. اگر سرور کرش کند یا سوکت‌ها بدون رویداد disconnect از بین بروند، کلید خودش منقضی می‌شود.
- وضعیت `offline` با TTL بلند (۳۰ روز) ذخیره می‌شود تا `lastSeen` مدتی باقی بماند.
- **بدون Redis:** fallback حافظه‌ای (Map) — همان الگوی محدودساز نرخ گام ۱؛ سرویس بالا می‌ماند و health فقط degraded گزارش می‌شود.

### چرخه حضور

- `handleConnection`: اگر **اولین socket** این کاربر است (شمارش socketها به تفکیک کاربر — پشتیبانی multi-device) → `setOnline` + broadcast
- `handleDisconnect`: اگر **آخرین socket** بسته شد → `setOffline` + broadcast
- broadcast به **اتاق شخصی `user:{id}` همه هم‌مکالمه‌ها** (co-participants با یک کوئری distinct روی Participant) — نه به کل سرور

### REST

```
GET /api/v1/users/:id/presence   →  { userId, online, lastSeen }
```

## ۳. تایپینگ

- کلاینت → سرور: `typing {conversationId}` — throttle سمت کلاینت: حداکثر هر ۲٫۵ ثانیه در حین تایپ
- سرور:
  - **اعتبارسنجی عضویت** — فقط اگر socket در اتاق `conv:{id}` باشد (`client.rooms.has`)؛ غیرعضو با `{ok:false, error:{code:'NOT_A_PARTICIPANT'}}` رد می‌شود
  - **محافظت سرور** — حداکثر هر ۱٫۵ ثانیه به ازای هر socket (Map با پاک‌سازی در disconnect)
  - انتشار با `client.to(room)` → به خود فرستنده echo نمی‌شود
- سرور → کلاینت: `typing {conversationId, userId}` — کلاینت‌ها «در حال نوشتن…» را ۴ ثانیه نمایش می‌دهند یا تا رسیدن رویداد بعدی

## ۴. رسید خواندن

- سرور از قبل در `markRead` رویداد داخلی `conversation.read` صادر می‌کرد؛ حالا gateway آن را به رویداد WS **`message.read {conversationId, userId, lastReadSeq}`** به اتاق مکالمه تبدیل می‌کند.
- کلاینت‌ها `peerLastRead` را نگه می‌دارند (مقدار اولیه از `conversation.peer.lastReadSeq`) و در رویداد فقط جلو می‌روند (`max`).
- نمایش در حباب پیام‌های خودم: `serverSeq <= peerLastRead` → **✓✓** وگرنه **✓**؛ پیام در حال ارسال «…» و ناموفق «✗».
- صفحه گفتگوها هم روی `message.read` رفرش می‌شود تا نشان نخوانده پس از خواندن در دستگاه دیگر صفر شود.

## ۵. همگام‌سازی آفلاین (`since`)

```
GET /api/v1/conversations/:id/messages?since=<seq>&limit=200
→ { messages: [صعودی], hasMore, nextBefore: null, nextSince: <seq> | null }
```

- `since` اولویت دارد؛ `before` (صفحه‌بندی به عقب گام ۲) دست‌نخورده باقی مانده — رگرسیون تست شد.
- کلاینت‌ها در رویداد `connect` سوکت (بعد از هر قطع/وصل): عضویت مجدد در اتاق + گرفتن پیام‌های `since = بزرگ‌ترین serverSeq موجود` + تازه‌سازی حضور طرف مقابل.
- dedupe با `clientMsgId` تضمین می‌کند پیامِ هم‌زمانِ تحویل‌شده از WS و sync دوبار نمایش داده نشود.

## ۶. کلاینت‌ها

- **موبایل:** هدر چت دو خطی (نام + وضعیت)، heartbeat در `socket.ts` (مختص اتصال فعال)، throttle typing در composer، ✓/✓✓ در حباب‌ها، sync در reconnect
- **دسکتاپ:** همان‌ها در `app.js` + عنصر `chatStatus` زیر عنوان چت با رنگ‌بندی (آنلاین سبز، در حال نوشتن آبی)
- هر دو کلاینت `serverSeq = MAX_SAFE_INTEGER` را به‌عنوان پیام خوش‌بینانه (بدون seq واقعی) از محاسبه sync مستثنا می‌کنند.

## ۷. نتایج تست دود (۱۷/۱۷)

ورود دو کاربر و مکالمه · presence آنلاین هر دو پس از اتصال · رویداد `presence.update` هنگام قطع + lastSeen · `typing` بلادرنگ · **throttle سرور** (۴ emit پشت هم ≤ ۲ رویداد) · رد typing غیرعضو · `message.read` بلادرنگ با lastReadSeq صحیح · `since=1` → پیام‌های ۲..۶ صعودی · `since=0&limit=2` با `nextSince=2` · ادامه sync از `nextSince` · رگرسیون `before` · کاربرِ بدون اتصال offline با lastSeen ثبت‌شده · ack heartbeat.

## ۸. محدودیت‌های شناخته‌شده

- انقضای TTL پس از سقوط سرور تا رویداد بعدی (heartbeat/reconnect) نادیده گرفته می‌شود — برای multi-node در گام عملیاتی با Redis adapter و sweep دوره‌ای کامل می‌شود.
- presence «در حال تایپ در لیست گفتگوها» (پیش‌نمایش) نمایش داده نمی‌شود — فقط داخل چت.
- sync آفلاین فعلاً فقط برای مکالمه باز انجام می‌شود؛ sync پس‌زمینه همه مکالمه‌ها با unreadCount جبران می‌شود (شمارنده سمت سرور درست است).
